## Measurement and scaling

- Small is the 8-commit shop demo plus deterministic Python edits. Medium and large start at 50 and 200 first-parent commits touching Flagsmith api/. All upstreams are local. Each interval advances the same next commit to every repo at one seeded uniform phase.
- Manual checks use a fixed cadence with a seeded phase per repo. The cadence is compressed by benchmark interval / 300, preserving the visit-to-commit rate ratio. Auto-followed repos rely on the scheduler; the remaining repos use manual checks.
- A follows zero repos. B follows the first two, or the only repo in the one-repo case. C follows all repos.
- Puppeteer Core drives system Chrome with cold navigation storage. Full Chrome uses a fresh context. The macOS headless shell clears storage and disables HTTP caching between samples. Readiness is a complete repository list, the selected preview, and the expected count of loaded sync switches. The isolated web server returns preview flags using the configured Development client key; timings exclude external Flagsmith network latency.
- A browser sample overlaps sync if its navigation-to-ready window intersects an observed Git ls-remote start to commit-index publication window for any repo.
- Loopback wall time through response body and JSON decoding. Probe cycles target 0.5 seconds, read every repo's commits, and rotate the newest diff across repos. Slow API calls can extend a cycle.
- One-second server-process samples. Git subprocess CPU and Chrome CPU are outside this measurement. CPU includes the API, including cache rebuilds after publishing, and uses a short warmed baseline with the same probes.
- Automatic refresh runs and analysis counts come from GET /api/auto-sync. Manual starts use its manual_runs counter, with POST attempts logged separately. Git Trace2 counts actual fetch calls; new snapshot files count the graphs built, including any missing base. Manual fetches and graphs are totals minus the automatic counters.
- Per-hour projections use the observed mixture of refresh costs and assume it carries over to 300 seconds. Benchmark intervals and reviewer visits control the workload. Treat projections as estimates, and review overlap counts and sample sizes.

Formulas

- **percentiles** — Sort the samples and linearly interpolate at (n - 1) × percentile.
- **observed_per_hour** — Observed counts and server CPU seconds × 3600 / observed elapsed seconds; CPU uses the elapsed time between its boundary samples.
- **idle_cpu_s_per_hour** — Measured server CPU seconds during warm baseline × 3600 / baseline CPU sample elapsed seconds. The baseline includes API and browser sampling.
- **refresh_cpu_s** — max(0, observed CPU seconds - idle CPU seconds/hour × observed CPU sample elapsed / 3600) / observed refresh jobs. Zero when no job ran.
- **default_refreshes_per_hour** — Auto-followed repos × 3600 / 300 + manually checked repos × visits per repo per hour.
- **default_cpu_ms_per_hour** — 1000 × (idle CPU seconds/hour + refresh CPU seconds × default refresh jobs/hour).
- **default_fetches_and_analysis_per_hour** — Observed count per refresh × default refresh jobs/hour, using the measured workload's mean cost per job.
- **default_advances_per_hour** — Repository count × 3600 / 300 (one new commit per repo per interval).
- **observed_freshness_s** — First /commits response containing the new SHA minus the upstream advance time.
- **measured_detection_to_visible_s** — First /commits response containing the SHA minus the later of the advance and the refresh start (Git ls-remote for auto, accepted manual POST for manual). Includes polling and any API wait.
- **default_freshness_s** — Measured detection-to-visible seconds + a seeded uniform wait of 0–300 seconds for auto or 0–(3600 / visits per repo per hour) for manual. The recorded samples use the benchmark seed; the simulator draws a new seeded wait per identity.
- **disk_growth_bytes** — Final minus initial logical file bytes in the data directory; hardlinked copies count once per directory.
